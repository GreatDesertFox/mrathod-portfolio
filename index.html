About me

Game and simulation software, end to end, since 2012.

Fourteen years building game software — mobile games for most of it (board games, endless runners, cricket sims, idle RPGs), and before that, healthcare and enterprise training simulations, plus a stretch of AR and HoloLens work for the automotive industry. Long enough to have shipped across most genres, and to know the hard part is rarely the feature. It's making the feature hold up on a three-year-old phone, on a deadline, with a team that has to keep working on it after I move on.

My core has been Unity3D and C# since 2012. These days I work as much on the server as the client — Go for game servers, backend services and tooling. I also spend a lot of time on the unglamorous half of the job: build pipelines, profiling, and the editor tools that let designers tune a game without booking a programmer.

What I get called in for

Make the game feel right.

Most gameplay problems are feel problems wearing a logic costume. I build the systems that decide how a game responds — turn flow, progression, economy, the moment-to-moment feedback — then tune them until they read correctly to a player who will never see the code.

  • Core gameplay, end to end — turn flow, combat, progression, economy and the feedback that makes each one legible to a player.
  • Live-ops features on games already in players' hands, without breaking the build.
  • Untangling monoliths into systems that can be changed independently.
  • Analytics that answer a question, instrumented so the team can see which parts of a design are actually working.

Make every frame count.

A mobile game lives or dies on the cheapest phone that runs it. I profile first, find the real cost, and fix that — batching, instancing, atlasing, memory and asset budgets — rather than optimizing whatever is easiest to reach.

  • Draw call reduction — static batching, GPU instancing and sprite atlases, down from the hundreds to under fifty.
  • Frame rate recovery on low-end devices, taking a game from half rate to near-locked.
  • Memory and asset budgets — profiling what actually costs, not what looks expensive.
  • Platform bugs others gave up on, including silent failures that only show as a retention dip.

Remove friction from production.

The fastest way to speed up a team is to stop making them wait. Build automation, asset pipelines, and tuning tools that let designers change the game without booking a programmer.

  • Build automation and CI/CD that turns a release from an event into a routine.
  • Addressable asset pipelines, so content ships without a client update.
  • Runtime tuning tools that let designers configure gameplay with no code dependency.
  • QA tooling — cheats, state jumps and harnesses that cut the time to reproduce a bug.
  • Server work in Go — authoritative game servers and the backend services behind live features: player state, matchmaking and progression.
